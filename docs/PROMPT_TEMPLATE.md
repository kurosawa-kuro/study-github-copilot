## 結論

GitHub Copilot 用プロンプトテンプレート（プログラミング工程）の改訂版（v3）。

v2 までは「調査→計画→実装→レビュー」の **実装フェーズだけ** をカバーしていた。v3 では工程全体の中での欠落（上流・下流・ループ）を補う:

| 欠落 | v3 での対応 |
|---|---|
| 上流（要件・設計）の欠落 | **Step 0 系**（要件明確化・設計判断・前提固定）を追加 |
| 下流（統合・デプロイ）の欠落 | **Step 5 系**（統合検証・デプロイ準備・振り返り）を追加 |
| ループ構造の不在（Step 4 で問題発見時の戻り先） | **戻り先判定ルール** を Step 4 に組み込み |

**注意**: 4 Phase 構造自体（Step 1〜4）は構造的に正しいので維持。見直しの本質は「中身」ではなく「前後」。

## 工程全体マップ

```
[上流: Step 0 系]                [実装本体: Step 1-4]                [下流: Step 5 系]
─────────────────              ────────────────────              ─────────────────
0-A 要件明確化      ──▶  1 調査 ──▶ 2 計画 ──▶ 3 実装 ──▶ 4 レビュー  ──▶  5-A 統合検証
0-B 設計判断（保留）            ▲                          │                  5-B デプロイ準備
0-C 前提固定                    └─────── ループ戻り ◀──────┘                  5-C 振り返り（保留）
```

- 上流: 案件開始時に1回実行
- 実装本体: Step 3-4 を Phase ごとに繰り返す（`{N}` を 1, 2, 3 … に置換）
- 下流: 実装完了後に1回実行

> **クイックガイドは別ファイル**: 早見表・案件規模別フロー・タグ一覧・戻り先判定は [QUICK_GUIDE.md](QUICK_GUIDE.md) を参照。

## プロンプトテンプレート

````markdown
GitHub Copilot プロンプト例（プログラミング工程・v3）

> **使い方**
> 1. 案件開始時: Step 0-A → 0-C を順に実行（曖昧さ排除と前提固定）
> 2. 実装本体: Step 1 → 2 → 3 → 4 の順に実行。Step 3-4 は Phase ごとに繰り返す
> 3. 実装完了後: Step 5-A → 5-B を実行（統合検証とデプロイ準備）
> 4. `[...]` プレースホルダーは実内容に置換、`{N}` は Phase 番号に置換
> 5. Phase {N} 開始時、コンテキスト落ち防止のため Step 0-C を再貼り付け推奨

## Step 0-A | 要件明確化（案件開始時、依頼内容が曖昧なとき）

```
依頼内容を構造化し、曖昧さを Copilot が暗黙補完しない状態にします。

- 入力: [依頼内容の生テキスト]

### 構造化観点
1. 達成したいこと（What）: ユーザー視点で1〜3行
2. 完了の判定基準（Done）: 観測可能な事象で記述
3. 制約・前提（Constraints）: 守るべき要件・触れない領域
4. 範囲外（Non-Goals）: 明示的にやらないこと

### 曖昧さの検出
- 解釈の分岐がある記述には [AMBIGUITY] タグを付け、分岐候補を列挙
- 想定ユーザー・実行環境・データ規模など暗黙の前提は [QUESTION] で問い返す
- 既存実装との関係が不明な箇所は [QUESTION] で停止

### 禁止事項
- 曖昧な箇所を勝手に解釈して構造化を完了させること
- 「一般的にはこうである」と暗黙の前提で埋めること

### 出力
- 構造化結果（What / Done / Constraints / Non-Goals）
- [AMBIGUITY] / [QUESTION] の列挙
- すべての [QUESTION] が解消されてから Step 0-C / Step 1 に進む
```

## Step 0-C | 前提固定（セッション開始時に1回実行）

```
このセッション全体で守るべき前提を確認・固定します。
以下を確認し、不足・矛盾があれば指摘してください。

### 技術スタック（Python / Redis / Terraform / GCP 中心）
- アプリ言語: Python 3.12（補助スクリプト: Bash）
- IaC: Terraform [例: 1.7.x]（HCL）
- クラウド: Google Cloud (GCP) / プロジェクト ID: [プロジェクト ID]
- 主要 GCP サービス: [例: Cloud Run / Cloud Functions / Vertex AI / BigQuery / Cloud Storage / Pub/Sub / Secret Manager / Memorystore for Redis]
- Redis: Memorystore for Redis もしくは自前運用 / クライアント: redis-py（必要に応じて async） / 用途: [例: キャッシュ / セッション / Pub/Sub / レートリミット / ジョブキュー]
- Python フレームワーク: [例: FastAPI / Flask / Cloud Functions Framework]
- テスト: pytest（Python）/ fakeredis または testcontainers-redis（Redis 単体）/ terraform validate・tflint・terraform plan（IaC）
- リンター・フォーマッター: ruff（Python）/ terraform fmt（HCL）
- 型チェック: mypy strict
- 依存管理: [例: uv / poetry / pip-tools]
- 認証: [例: ADC / Service Account Key / Workload Identity Federation]

### コーディング規約
- Python 命名: PEP 8（関数・変数 snake_case、クラス PascalCase、定数 UPPER_SNAKE_CASE）
- Terraform 命名: リソース型は snake_case、name 属性は kebab-case
- Redis キー命名: コロン区切りの名前空間（例: `app:<feature>:<id>`）、用途と TTL をコード側コメントで明示
- ディレクトリ構成:
    - Python: [例: src/<package>/、tests/]
    - Terraform: [例: terraform/envs/<env>/、terraform/modules/]
- 既存規約ドキュメント: [パス]

### 制約
- 後方互換性: [必須 / 不要]
- 性能要件: [例: API p95 < 200ms / Cloud Run コールドスタート許容]
- 依存追加: [自由 / 要承認 / 禁止]
- セキュリティ: 機密情報は Secret Manager、ハードコード禁止
- IaC 原則: 手動変更禁止（必ず terraform 経由）、state 衝突回避（remote backend）
- Redis: TTL 必須（メモリ枯渇防止）、永続化方針 [例: RDB / AOF / なし]、最大メモリポリシー [例: allkeys-lru]、キー数・メモリ上限を監視対象に

### 出力ルール（全Stepで遵守）
- 推測した箇所は [ASSUMPTION] タグを付けて明示
- 確認したい事項は [QUESTION] タグで列挙し、勝手に決定しない
- 既存コードに反する変更は [BREAKING] タグで警告
- タグなしで推測・決定した出力は不完全とみなす

確認後、「前提固定完了」と出力してください。
```

## Step 1 | 実現可能性の調査

```
以下の要件について、現在のコードベースで実現可能性を調査してください。

- 要件: [Step 0-A の構造化結果 もしくは 依頼内容]
- 参照: [仕様書パス] / [リポジトリパス]

### 調査手順（必ずこの順で）
1. 既存コードの関連箇所を grep / 構造解析で特定し、ファイルパスと行番号を列挙
2. 影響範囲を「直接変更」「間接影響」「未影響」の3層で分類
3. 技術的制約（既存設計、依存ライブラリ、性能要件との衝突）を洗い出し
4. 代替案を最低2つ提示し、トレードオフを比較

### 出力フォーマット
- 実現可否: ◯ / △（条件付き） / ×
- 根拠: 上記1〜3の調査結果（事実とコード根拠を明示）
- 推奨案: 代替案のうち1つを選定、選定理由を明記
- 懸念点: 残存リスクを列挙
- 未確定事項: [QUESTION] タグで列挙（勝手に決めない）

### 禁止事項
- 推測のみで「実装可能」と断定すること
- 既存コードを確認せず一般論で回答すること
- [ASSUMPTION] / [QUESTION] タグなしで不明点を埋めること
```

## Step 2 | 作業計画書の作成

```
Step 1 の調査結果をもとに作業計画書を作成してください。

### Phase 分割ルール
- 1 Phase = 1コミットで完結する単位
- 1 Phase の変更行数目安: 300行以内（超える場合は再分割）
- 各 Phase 単独で動作・テスト可能であること（積み上げ式）

### 各 Phase の記載項目
- 目的（1〜2行）
- 前提: 直前 Phase の成果物・引き継ぎ事項
- 変更/新規ファイル一覧（表: パス | 種別 | 変更概要 | 想定行数）
- 公開インタフェース（関数シグネチャ・型定義）のみ ※本体実装は書かない
- 完了条件（必ず以下3種をすべて含む）
    - 機能条件: [例: エンドポイント /users が 200 を返す]
    - テスト条件: [例: 新規ユニットテストが全パス、カバレッジ XX%以上]
    - 検証コマンド: [例: `pytest tests/users/`、`curl ...`]
- ロールバック手順（1行）

### 全体まとめ
- 推奨実行順と理由
- Phase 間の依存関係図（テキスト or Mermaid）
- リスクと対策（表: リスク | 発生確率 | 影響 | 対策）
- 中止判断条件: どの Phase でどの状況が起きたら全体を中断するか

### 補足
- UI 変更・ドキュメント・設定ファイル等で検証コマンドが書けない場合は、
  「目視確認手順」を代替として明記すること
- インフラ系の Phase は `terraform plan` の差分を検証コマンドとして使う
```

## Step 3 | Phase {N} の実装

```
作業計画書の Phase {N} を実装してください。

### 実装手順
1. Phase {N} の完了条件・検証コマンドを再掲してください
2. テストコードを先に書き、失敗することを確認（Red）
3. 最小実装で通す（Green）
4. リファクタ（Refactor）
5. 検証コマンドを実行し、出力をそのまま貼り付け

### テスト要件
- 正常系: 最低1つ
- 異常系: 最低1つ（エラーハンドリングが必要な場合）
- 境界値: 必要に応じて

### 制約
- Phase {N} の範囲を超える変更は禁止
- 範囲外の改善余地を見つけた場合は [OUT-OF-SCOPE] として列挙のみ（実装しない）
- 既存テストを変更する場合は [BREAKING] タグで報告
- 不明点は推測せず [QUESTION] で停止
- コメントは WHY が非自明な箇所のみ（コードを読めば分かる WHAT は書かない）

### 出力
- 変更ファイル一覧と diff サマリー
- 検証コマンド実行結果（pass/fail と実出力）
- [OUT-OF-SCOPE] / [QUESTION] / [BREAKING] の有無
```

## Step 4 | Phase {N} のレビュー（独立観点 + 戻り先判定 + 引き継ぎ）

```
Phase {N} の実装を、以下の独立した観点でレビューしてください。
**実装時の判断を擁護せず、批判的に検証してください。**

### レビュー観点
1. 完了条件の機械的検証
    - 検証コマンドの実行結果を再掲
    - 失敗があれば修正案を提示
2. 要件適合性
    - 依頼要件と実装の対応表を作成
    - 漏れ・過剰実装を指摘
3. 副作用検査
    - 変更箇所が import / 呼び出されている全箇所を列挙
    - 既存テストへの影響を確認
4. コード品質
    - 命名・責務分離・エラーハンドリング
    - テストの網羅性（正常 / 異常 / 境界）
5. セキュリティ・性能
    - 入力検証、SQL / コマンドインジェクション、N+1、メモリリーク

### 戻り先判定（× または △ がある場合は必須）
問題の種類に応じて戻り先を1つ選び、「戻り先: Step X」と明記してから修正案を提示:

| 問題の種類 | 戻り先 |
|---|---|
| 軽微な実装バグ・テスト漏れ | Step 3（同 Phase 内修正） |
| 完了条件の不備・Phase 分割ミス | Step 2（計画再策定） |
| 要件・既存コードとの矛盾、影響範囲の見落とし | Step 1（調査やり直し） |
| 設計上の欠陥（アーキテクチャ破綻） | Step 0-B（再設計） |
| 要件自体の曖昧さ・誤解 | Step 0-A（要件明確化） |

### 出力フォーマット
- 観点別の判定: ◯ / △ / ×（各観点に一言根拠を添える）
- × または △ がある場合: 戻り先と修正案を提示し、Phase {N} は未完了とする
- すべて ◯ かつ検証コマンドが pass の場合のみ
  「Phase {N} 完了。次の Phase {N+1} に進んでください」と出力

### Phase 間引き継ぎメモ（完了時のみ必須）
次の Phase に引き継ぐべき以下を JSON で出力:

{
  "completed_phase": {N},
  "key_decisions": ["..."],
  "deferred_items": ["..."],
  "assumptions_made": ["..."],
  "breaking_changes": ["..."],
  "out_of_scope_items": ["..."]
}
```

## Step 5-A | 統合検証（実装完了後、複数 Phase 完了時）

```
複数 Phase をまたいだ整合性を検証します。

- 対象: 完了済み Phase 1〜{N} 全体
- 入力: 各 Phase の Step 4 引き継ぎ JSON

### 検証観点
1. Phase 間整合性
    - 引き継ぎ JSON を時系列で再掲
    - assumptions_made / breaking_changes が後続 Phase で消化されているか確認
2. E2E 動作
    - ユーザーシナリオ単位で動作確認手順を列挙し、実行結果を貼り付け
    - 既存機能のスモークテストを実行
3. 累積副作用
    - Phase 単独では見逃される相互作用を点検
        - パフォーマンス劣化（API レイテンシ、メモリ）
        - ログ過多 / 監視ノイズ
        - 依存ライブラリの重複・バージョン衝突
4. 残存 [OUT-OF-SCOPE] の棚卸し
    - 各 Phase で先送りした項目を一覧化
    - 本リリースに含めるか / 別チケットに切るかを判定

### 出力
- 観点別の判定: ◯ / △ / ×
- × がある場合: 該当 Phase に差し戻す（戻り先を明記）
- 残存 [OUT-OF-SCOPE] の処理方針
- 統合完了宣言（すべて ◯ の場合のみ）
```

## Step 5-B | デプロイ準備（本番投入前）

```
本番投入前のチェックリストを実行します。

- 対象: Step 5-A を通過した変更一式

### チェック項目
1. IaC / マイグレーション
    - `terraform plan` の差分が想定通りか（不可逆な変更の有無）
    - DB マイグレーションの ロールフォワード / ロールバック手順
    - DROP / データ削除など破壊的変更の承認状況
2. デプロイ手順
    - リリースコマンド / デプロイパイプライン
    - 段階リリース戦略（カナリア / ブルーグリーン / 即時）
    - 切り戻し手順（コマンドレベルで明記）
3. 監視・観測
    - 追加すべきメトリクス / アラート
    - 関連ダッシュボードのリンク
    - SLO への影響
4. 影響範囲・告知
    - ダウンタイム想定
    - 関係者への通知要否

### 出力
- チェック項目別の判定と根拠
- 「デプロイ可能」または「デプロイ前に [QUESTION] / [BLOCKER] を解消」の判定
```

> プロセス改善のための学習抽出。複数案件で同種の問題が再発したら整備する。
````

## ループ構造（全体）

Step 4 のレビュー結果に応じて、修正の戻り先を明示的に選ぶ。Copilot に「自動でやり直す」を任せず、ルール化して人間の判断と整合させる。

```
        ┌──────────────────────────────────────────────────────┐
        │                                                      │
        ▼                                                      │
Step 0-A ─▶ Step 0-C ─▶ Step 1 ─▶ Step 2 ─▶ Step 3 ─▶ Step 4 ──┘
   ▲          ▲          ▲          ▲          ▲       │ │
   │          │          │          │          └───────┘ │ 軽微バグ
   │          │          │          └────────────────────┘ 計画ミス
   │          │          └───────────────────────────────── 要件矛盾
   │          └──────────────────────────────────────────── （0-B 再設計、保留中）
   └─────────────────────────────────────────────────────── 要件の曖昧さ
```

## 運用上の留意点（破綻条件と対処）

| 破綻条件 | 兆候 | 対処 |
|---|---|---|
| Copilot のコンテキスト窓を超える | Phase {N} 実装中に Step 0-C の前提を忘れる | Phase 開始時に Step 0-C を再貼り付け |
| タグ運用が形骸化 | `[ASSUMPTION]` / `[AMBIGUITY]` が出力されない | Step 0-C の「タグなし出力は不完全」を再周知 |
| 検証コマンドが書けない領域 | UI 変更、ドキュメント、設定ファイル | Step 2 で「目視確認手順」を代替記載 |
| 大規模リファクタ | Phase が 10 超 | プロンプト工程ではなく設計レビューを先行 |
| 案件規模が小さい（数時間で終わる修正） | Step 0-A / 5 系が形骸化 | Step 1〜4 のみで実行、Step 0-C だけ追加 |
| 要件が完全に固まっている | Step 0-A が冗長 | Step 0-C のみ実行して Step 1 へ |
| Claude Code 主体で対話的に進める | プロンプト体系自体が過剰 | テンプレ管理ではなく対話で代替 |

## 段階導入ガイド

**即時導入推奨（コスト低・効果高）**
- Step 0-C（前提固定） → コピペで導入可能
- タグ運用（`[ASSUMPTION]` / `[AMBIGUITY]` / `[QUESTION]` / `[OUT-OF-SCOPE]` / `[BREAKING]`）
- Step 4 の戻り先判定 → 自己採点バイアスと「やり直し迷子」を同時に排除
- 完了条件への「検証コマンド」必須化

**1週間後導入（運用慣れ後）**
- Step 0-A（要件明確化） → 曖昧な依頼を投げる事故を防ぐ。効果大

**1ヶ月後導入（本番運用フェーズ）**
- Step 5-A（統合検証） → 3 Phase 以上の中規模タスクで効果

## 領域別の適用差

| 案件特性 | 重点 Step | 理由 |
|---|---|---|
| ML 系（Vertex AI、Elasticsearch 等） | 0-A, 0-B, 5-A | 要件と設計の曖昧さが大きい。実験的性質 |
| インフラ系（GCP、Terraform） | 0-C, 5-B | 前提固定と plan 検証が決定的に効く |
| 既存システム改修 | 1, 4, 5-A | 影響範囲調査と副作用検査が中核 |
| 新規実装（小規模） | 0-C, 2, 3, 4 | 要件が明確なら 0-A 省略可 |
