# GitHub Copilot プロンプト クイックガイド

## 規模別フロー

| 規模 | フロー |
|---|---|
| 小規模（数時間） | `0-C → 1 → 3 → 4` |
| 標準（数日〜週） | `0-A → 0-C → 1 → 2 → [3 → 4]×N → 5-A` |
| 大規模（本番投入） | `0-A → 0-B → 0-C → 1 → 2 → [3 → 4]×N → 5-A → 5-B` |
| インフラ専業 | `0-C → 1 → 2 → [3 → 4]×N → 5-B` |

## タグ

| タグ | 意味 / 対応 |
|---|---|
| `[ASSUMPTION]` | 推測で埋めた → 人間が妥当性確認 |
| `[QUESTION]` | 確認事項 → 回答して再実行 |
| `[AMBIGUITY]` | 解釈の分岐 → 分岐を指示 |
| `[OUT-OF-SCOPE]` | 範囲外 → 別チケット化 |
| `[BREAKING]` | 既存に反する → 影響確認 |
| `[BLOCKER]` | デプロイ阻害 → 解消必須 |

タグなし出力は不完全とみなして再実行。

## 戻り先（Step 4 で問題発見時）

| 問題 | 戻る |
|---|---|
| 軽微な実装バグ・テスト漏れ | Step 3 |
| 完了条件の不備・Phase 分割ミス | Step 2 |
| 要件・既存コードとの矛盾 | Step 1 |
| 設計上の欠陥 | Step 0-B |
| 要件の曖昧さ・誤解 | Step 0-A |

---

# プロンプト本体

`[...]` を実内容に置換、`{N}` を Phase 番号に置換して Copilot に貼り付け。

## Step 0-A | 要件明確化

```
依頼内容を構造化し、曖昧さを Copilot が暗黙補完しない状態にします。

- 入力: [依頼内容の生テキスト]

### 構造化観点
1. 達成したいこと（What）: ユーザー視点で1〜3行
2. 完了の判定基準（Done）: 観測可能な事象で記述
3. 制約・前提（Constraints）: 守るべき要件・触れない領域
4. 範囲外（Non-Goals）: 明示的にやらないこと

### 曖昧さの検出
- 解釈の分岐がある記述には [AMBIGUITY] タグを付け、分岐候補を列挙
- 想定ユーザー・実行環境・データ規模など暗黙の前提は [QUESTION] で問い返す
- 既存実装との関係が不明な箇所は [QUESTION] で停止

### 禁止事項
- 曖昧な箇所を勝手に解釈して構造化を完了させること
- 「一般的にはこうである」と暗黙の前提で埋めること

### 出力
- 構造化結果（What / Done / Constraints / Non-Goals）
- [AMBIGUITY] / [QUESTION] の列挙
- すべての [QUESTION] が解消されてから Step 0-C / Step 1 に進む
```

## Step 0-B | 設計判断（保留）

> v3 では未整備。以下の **トリガ** が満たされたら v4 で整備する:
> - 同一プロジェクトで「アーキテクチャ判断が必要」と判定された案件が 2 件以上発生
> - または、戻り先判定「Step 0-B」が他プロジェクトを含めて 3 件以上発生
>
> それまでは Step 0-A の `[AMBIGUITY]` 列挙で設計判断のばらつきを吸収する。
> 戻り先判定表で「設計欠陥 → Step 0-B」となった場合、暫定的に Step 0-A まで戻して設計選択肢を `[AMBIGUITY]` で再列挙する。

## Step 0-C | 前提固定

セッション開始時に **0-C-full** を 1 回貼る。Phase 開始時のコンテキスト落ち対策には **0-C-min** を再貼り付けする。

### Step 0-C-min（Phase 毎に再貼り付け・約 10 行）

```
このセッションの前提を再確認します。逸脱があれば指摘してください。

- 言語/フレームワーク: [例: Python 3.12 / FastAPI]
- 依存管理: [例: uv]
- テスト: [例: pytest + fakeredis]
- 後方互換性: [必須 / 不要]
- 出力ルール: 推測は [ASSUMPTION] / 確認事項は [QUESTION] / 既存に反する変更は [BREAKING]
- タグなしで推測・決定した出力は不完全とみなす

「前提了解」とだけ出力してください。
```

### Step 0-C-full（セッション開始時に 1 回）

```
このセッション全体で守るべき前提を確認・固定します。

### 技術スタック（Python / Redis / Terraform / GCP 中心）
- アプリ言語: Python 3.12（補助: Bash）
- IaC: Terraform [例: 1.7.x]
- クラウド: GCP / プロジェクト ID: [プロジェクト ID]
- 主要 GCP サービス: [例: Cloud Run / Cloud Functions / Vertex AI / BigQuery / Cloud Storage / Pub/Sub / Secret Manager / Memorystore for Redis]
- Redis: Memorystore for Redis または自前 / クライアント: redis-py / 用途: [例: キャッシュ / セッション / レートリミット / ジョブキューは永続化要件次第で自前運用]
- Python フレームワーク: [例: FastAPI / Flask / Cloud Functions Framework]
- テスト: pytest / fakeredis または testcontainers-redis / terraform validate・tflint・terraform plan
- リンター: ruff / terraform fmt
- 型チェック: mypy strict
- 依存管理: [例: uv / poetry]
- 認証: [例: ADC / Workload Identity Federation]

### コーディング規約
- Python: PEP 8（snake_case / PascalCase / UPPER_SNAKE_CASE）
- Terraform: リソース型 snake_case、name 属性 kebab-case
- Redis キー: コロン区切り名前空間（`app:<feature>:<id>`）、用途と TTL をコメントで明示
- ディレクトリ: Python = src/<package>/、tests/ ／ Terraform = terraform/envs/<env>/、terraform/modules/
- 既存規約ドキュメント: [パス]

### 制約
- 後方互換性: [必須 / 不要]
- 性能要件: [例: API p95 < 200ms / Cloud Run コールドスタート許容]
- 依存追加: [自由 / 要承認 / 禁止]
- セキュリティ: 機密は Secret Manager、ハードコード禁止
- IaC: 手動変更禁止、remote backend 必須
- Redis: TTL 必須、永続化方針 [RDB/AOF/なし]、最大メモリポリシー [例: allkeys-lru]

### 出力ルール（全Stepで遵守）
- 推測は [ASSUMPTION]、確認事項は [QUESTION]、既存に反する変更は [BREAKING]
- タグなしで推測・決定した出力は不完全

確認後、「前提固定完了」と出力してください。
```

**運用**: 0-C-full の埋め込み済み版を `docs/CONTEXT.md` 等にプロジェクト固有値で保存し、Phase 毎は 0-C-min だけを貼ると効率的。

## Step 1 | 実現可能性の調査

```
以下の要件について、現在のコードベースで実現可能性を調査してください。

- 要件: [Step 0-A の構造化結果 もしくは 依頼内容]
- 参照: [仕様書パス] / [リポジトリパス]

### 調査手順（必ずこの順で）
1. 既存コードの関連箇所を grep / 構造解析で特定し、ファイルパスと行番号を列挙
2. 影響範囲を「直接変更」「間接影響」「未影響」の3層で分類
3. 技術的制約を洗い出し
4. 代替案を最低2つ提示し、トレードオフを比較

### 出力
- 実現可否: ◯ / △ / ×
- 根拠: 上記1〜3の調査結果（事実とコード根拠を明示）
- 推奨案: 代替案のうち1つを選定、選定理由を明記
- 懸念点: 残存リスク
- 未確定事項: [QUESTION] で列挙（勝手に決めない）

### 禁止事項
- 推測のみで「実装可能」と断定
- 既存コードを確認せず一般論で回答
```

## Step 2 | 作業計画書

```
Step 1 の調査結果をもとに作業計画書を作成してください。

### Phase 分割ルール
- 1 Phase = 1コミットで完結する単位
- 変更行数目安: 300行以内
- 各 Phase 単独で動作・テスト可能（積み上げ式）

### 各 Phase の記載項目
- 目的（1〜2行）
- 前提: 直前 Phase の成果物
- 変更/新規ファイル一覧（表: パス | 種別 | 概要 | 想定行数）
- 公開インタフェース（シグネチャ・型）のみ ※本体実装は書かない
- 完了条件（3種すべて）
    - 機能条件: [例: /users が 200 を返す]
    - テスト条件: [例: 新規ユニットテストが全パス]
    - 検証コマンド: [例: `pytest tests/users/`]
- ロールバック手順（1行）

### 全体まとめ
- 推奨実行順
- Phase 間の依存関係図
- リスクと対策
- 中止判断条件

### 補足
- 検証コマンドが書けない領域は「目視確認手順」で代替
- インフラ系は `terraform plan` 差分を検証コマンドにする
```

## Step 3 | Phase {N} の実装

```
作業計画書の Phase {N} を実装してください。

### 実装手順
1. Phase {N} の完了条件・検証コマンドを再掲
2. テストを先に書き失敗確認（Red）
3. 最小実装で通す（Green）
4. リファクタ（Refactor）
5. 検証コマンドを実行し出力を貼り付け

### テスト要件
- 正常系: 最低1つ
- 異常系: 最低1つ
- 境界値: 必要に応じて

### 制約
- Phase {N} の範囲を超える変更は禁止
- 範囲外の改善は [OUT-OF-SCOPE] として列挙のみ
- 既存テスト変更は [BREAKING] で報告
- 不明点は推測せず [QUESTION] で停止
- コメントは WHY が非自明な箇所のみ

### 出力
- 変更ファイル一覧と diff サマリー
- 検証コマンド実行結果（pass/fail と実出力）
- [OUT-OF-SCOPE] / [QUESTION] / [BREAKING] の有無
```

## Step 4 | Phase {N} のレビュー

```
Phase {N} の実装を批判的に検証してください。実装時の判断を擁護しないこと。

### レビュー観点
1. 完了条件の機械的検証: 検証コマンド実行結果を再掲
2. 要件適合性: 依頼要件と実装の対応表、漏れ・過剰実装
3. 副作用検査: import / 呼び出し元の全箇所、既存テストへの影響
4. コード品質: 命名・責務分離・エラーハンドリング、テスト網羅性
5. セキュリティ・性能: 入力検証、インジェクション、N+1、メモリリーク

### 戻り先判定（× または △ がある場合）
| 問題 | 戻り先 |
|---|---|
| 軽微なバグ・テスト漏れ | Step 3 |
| 完了条件不備・分割ミス | Step 2 |
| 要件・既存矛盾 | Step 1 |
| 設計欠陥 | Step 0-B |
| 要件曖昧 | Step 0-A |

「戻り先: Step X」と明記してから修正案を提示。

### 出力
- 観点別の判定: ◯ / △ / ×（各観点に根拠1行）
- × / △ あり: 戻り先と修正案、Phase {N} は未完了
- すべて ◯ かつ検証コマンド pass: 「Phase {N} 完了。次の Phase {N+1} に進んでください」

### Phase 間引き継ぎ（完了時のみ）
JSON で出力:

{
  "completed_phase": {N},
  "key_decisions": ["..."],
  "deferred_items": ["..."],
  "assumptions_made": ["..."],
  "breaking_changes": ["..."],
  "out_of_scope_items": ["..."]
}
```

## Step 5-A | 統合検証

```
Phase 1〜{N} 全体の整合性を検証してください。
入力: 各 Phase の Step 4 引き継ぎ JSON

### 検証観点
1. Phase 間整合性: assumptions / breaking_changes が後続で消化されているか
2. E2E 動作: ユーザーシナリオ単位で実行結果を貼り付け、スモークテスト
3. 累積副作用: パフォーマンス劣化 / ログ過多 / 依存重複
4. 残存 [OUT-OF-SCOPE] の棚卸し: リリースに含めるか別チケット化か判定

### 出力
- 観点別判定: ◯ / △ / ×
- × あり: 該当 Phase に差し戻し（戻り先明記）
- 残存 [OUT-OF-SCOPE] の処理方針
- 統合完了宣言（すべて ◯ の場合のみ）
```

## Step 5-B | デプロイ準備

```
本番投入前のチェックリストを実行してください。
対象: Step 5-A を通過した変更一式

### チェック項目
1. IaC / マイグレーション
    - `terraform plan` 差分が想定通りか（不可逆変更の有無）
    - DB マイグレーションのロールフォワード / ロールバック
    - DROP / データ削除の承認状況
2. デプロイ手順
    - リリースコマンド / パイプライン
    - 段階リリース戦略
    - 切り戻し手順（コマンドレベル）
3. 監視・観測
    - 追加メトリクス / アラート、関連ダッシュボード、SLO 影響
4. 影響範囲・告知
    - ダウンタイム想定、関係者への通知要否

### 出力
- 項目別の判定と根拠
- 「デプロイ可能」または「[QUESTION] / [BLOCKER] 解消後」の判定
```

## Step 5-C | 振り返り（保留）

> v3 では未整備。以下の **トリガ** が満たされたら v4 で整備する:
> - 同種の Step 4 戻り先判定が他プロジェクトを含めて 3 件以上再発
> - または、複数案件で同じ `[OUT-OF-SCOPE]` 項目が繰り返し発生
>
> 単発案件では振り返り不要。複数案件にまたがる傾向が見えてから整備する。
