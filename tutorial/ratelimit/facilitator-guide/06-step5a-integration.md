# 06. Step 5-A 統合検証 — 何を見るか

## 入力

Phase 1〜3 の引き継ぎ JSON 3 つ。

## チェック項目

### 1. Phase 間整合性

- Phase 1 の `deferred_items`（コネクションプール）が Phase 2 で実害なく済んだか
- Phase 2 の `deferred_items`（設定外出し、ヘッダ整備）が Phase 3 で全消化されているか
- Phase 2 の `breaking_changes`（gateway 二重制御）に対する **判断**が引き継がれているか
  → 「監視で観察する」「ヘッダ衝突は Phase 3 で整備した」等の明示

### 2. E2E 動作

最低限、以下のシナリオを `curl` か `httpx` で叩いて結果を引き継ぎに貼り付け:

| シナリオ | 期待 |
|---|---|
| 認証あり `/users/u-001` × 60 回 | 全部 200、`X-RateLimit-Remaining` が 0 まで減る |
| 61 回目 | 429、`Retry-After: 60` |
| `/health` × 100 回 | 全部 200、レートリミットヘッダ無し |
| 認証なし `/users/u-001` | 401（既存挙動が壊れていないこと） |
| 異なる user_id（u-001 / u-002） | カウンタが独立していること |

### 3. 累積副作用

- `redis_client.py` の旧 API 残骸が無いか（`UserCacheRedis` の外部 API は不変のはず）
- `pytest` 全体の所要時間が極端に増えていないか（fakeredis なので増えない想定）
- ログ過多になっていないか（middleware で毎リクエスト print していないか）

### 4. 残存 `[OUT-OF-SCOPE]` の棚卸し

- ヘッダ命名の IETF 準拠 → **別チケット化推奨**
- 監視・アラート → **別チケット化必須**（依頼スコープ外、リリース前に立てる）
- スライディングウィンドウへの将来切替 → 保留

## 統合完了宣言

すべての観点が ◯ なら「統合完了」を出力。
1つでも × があれば該当 Phase に差し戻し（戻り先を明記）。

## ファシリの最終確認

- 受講者が Step 5-A の出力に **`/orders` の gateway 二重制御** について何らかの判断を書いているか
- 引き継ぎ JSON 3 つすべてが Git にコミットされているか
- 残存 [OUT-OF-SCOPE] が別チケット候補としてリストになっているか
